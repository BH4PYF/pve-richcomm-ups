# 原厂电量表修正（2026-10-29 36.7 分钟深度放电实测）

数据来源：`/var/log/ups-fastlog.csv`（1 秒原厂 SHM 快照，含完整 224 字节）、`/var/log/ups-screenlog.csv`（3 秒原厂屏幕）、用户万用表逐点实测、`ups-selftest-watch` 与 `ups-autoct` 日志。配对明细见 [meter-30min-2026-10-29.csv](../logs/meter-30min-2026-10-29.csv)。

## 1. 原厂电量表是查表，不是容量

原厂屏幕那行 `UPS Battery Level` 由单块 12 V 电压直接换算，闭式为：

```
charge% = round((V_block − 10.0) × 10) / 36 × 100
```

即每 0.1 V/块跳 2.7778%，整组满量程被压进 20.0 → 27.2 V。用 1 秒日志逐点验证：11.8 V/块 → 50.00%，12.7 → 75.00%，13.5 → 97.2%（浮充时屏幕显示 97% 正是此式结果）。

原厂电压 `fDc` 确实是实测 ADC（不是纯表值），但只有 0.1 V/块分辨率且带 ±1 格抖动；按分钟取平均可以把分辨率恢复到约 ±0.02 V，三个实测点均满足 **实测 = raw + 0.80 V**（误差 ≤0.10 V，浮充与带载放电两种状态都成立，`VOLTAGE_OFFSET=0.80` 无需改动）。

## 2. 实测配对（负载 18%，约 5.2 A / 105–126 W DC）

| t+ | 实测整组 | 原厂 raw | raw+0.80 | 误差 | 原厂电量 | 安时 SOC |
|---|---|---|---|---|---|---|
| 0:50 | 24.8 | 24.06 | 24.86 | −0.06 | 55.56% | 99.9% |
| 4:20 | 24.5 | 23.67 | 24.47 | +0.03 | 50.00% | 99.2% |
| 11:20 | 24.4 | 23.60 | 24.40 | −0.00 | 50.00% | 97.9% |
| 18:20 | 24.3 | 23.60 | 24.40 | −0.10 | 50.00% | 96.5% |
| 25:20 | 24.3 | 23.60 | 24.40 | −0.10 | 50.00% | 95.3% |
| 30:20 | 24.2 | （22:58:48 起失联） | | | — | 93.6% |

第 8 到第 30 分钟，原厂 raw **恒定为 23.600，抖动完全消失**，而同期真实电荷还在下降。两个结论：

- 0.1 V/块的步进约等于 5 分钟的真实压降，带载平台又极平（实测约 0.05 V 对应 1% SOC），所以**原厂电量表和整组电压都无法用来估 SOC**——顶端 7% 容量只花了 0.6 V。
- SOC 必须由能量/安时积分给出，电压只能当兜底判据。桥接的模型本来就是这样做的，本次实测把这条设计确认下来了。

按实测，36.7 分钟消耗 3.22 Ah = 额定 45 Ah 的 7.2%，即真实斜率 0.196%/min；模型给出 0.227%/min，**模型比实测保守约 16%**。因为 PF 与逆变效率仍属估算、且只放到 7% 深度，`RUNTIME_MINUTES=360` 保持不动（不要往上调）。附带一点：`RATED_WATTS` 在"可用能量 = 额定功率 × 参考负载 × 参考时长"的标定里会被约掉，改它不改变 SOC 与续航，所以也保持 400。

## 3. 已下发的修正

`/etc/ups-pve/runtime.conf`（备份 `runtime.conf.bak.37mintest`）——阈值现在是配置项，改完约 10 秒生效、无需重启：

```
VOLTAGE_DERATE_START=22.6   # 原 23.2：距实测平台 23.6 只有 0.4V，一断电就降额
VOLTAGE_CUTOFF=21.0         # 不变（续航外推零点，实测约 21.8V）
LB_VOLTAGE=21.6             # 不变：raw 21.6 = 实测 22.4 = 1.87V/格，按实测斜率约剩 20%
LB_SOC=20                   # 不变，改为可配置
```

`nut_bridge.py` 新增 `battery.charge.vendor`：把原厂那行百分比原样发布出来供对照，不参与任何计算，避免再被当成容量（本次它全程 50%，真实 SOC 93–100%）。同时新增 `shm_has_data()` 零数据判定（见下）。

网页卡片的 dashed 低压线随 `warn_voltage` 自动从 24.05 → 23.4 V。

## 4. 本次暴露的三个真实缺陷（已修）

1. **CT 没能发出。** 22:58:48 UPS 从总线上彻底消失（与用户两次拿表笔测电池的时刻重合，判断为线缆/接口接触），23:03:40 看门狗按点执行时 `ups-selftest` 报 `not found`，深度自检因此又多跑了约 7 分钟。修复：新增 `/usr/local/sbin/ups-autoct`——每秒扫 `lsusb`，设备一回来等 4 秒就自动 `stop ups-manager → ups-selftest cancel → start`。本次 23:10:25 就是它把 CT 补发成功的。
2. **看门狗误报"测试已停止"。** 它只认 `self_test` 字段，而重启后的 `ups_monitor` 因打不开 HID 句柄把 SHM 清零、所有字段都打印 Normal，于是被当成"测试结束"。修复：读数为零（`pack_v ≤ 5`）视为无信息、继续等待，并累计告警提示检查 hiddev。
3. **原厂盲但下游显示正常。** 重新插拔后内核把 hiddev0 注册为 180:0，而 `/dev/usb/hiddev0` 仍是旧的 180:96，`ups_monitor` 对每个 hiddev 索引 open 全部 ENODEV，却"进程活着、设备在总线上"，桥接因此判定链路正常并发布 `OL TRIM`、电压 0.0。修复：`/usr/local/lib/ups-pve/fix-hiddev.sh` 按 sysfs 的 dev_t 重建节点，已挂到 `ups-manager.service` 的第一条 `ExecStartPre`（已实测：把节点改回 180:96 后 open 失败，脚本一跑即恢复）；桥接同时增加 `shm_has_data()`，零数据计入失联计数，3 个周期后照旧走 ALARM + 钉钉 + 卡片"通信中断"。

顺带修掉：`ups-fastlog.py` 硬编码的 `DISPLAY_OFFSET=0.85` 改为读 `runtime.conf`（此前它的 `pack_display` 列比其它消费者高 0.05 V）。
